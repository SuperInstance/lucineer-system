# Research Brief: AI Agents That Build In Games
## Architecture Analysis & Recommendations for a Roblox AI Building Companion

**Compiled:** 2026-08-01  
**Purpose:** Inform design of a persistent OpenClaw-backed AI companion for Roblox

---

## 1. MINDcraft (Andy the Bot)

**Project:** [github.com/kolbytn/mindcraft](https://github.com/kolbytn/mindcraft)  
**Creators:** Kolby Nottingham & Max Robinson (UC Irvine)  
**Default bot:** "Andy"  
**Era:** Post-Voyager (late 2023 onward), actively developed through 2024-2025

### Architecture

MINDcraft is a **Node.js application** built on the **Mineflayer** library, which provides a programmatic API to Minecraft (not screen-image based). This is the critical design choice — instead of perceiving the world through pixels and outputting mouse/keyboard events, the bot interacts with Minecraft through **high-level code**.

**Core loop (`handleMessage`):**
```
1. Player sends natural language message
2. Message added to conversation history
3. Full history sent to LLM (GPT-4 / Claude / Gemini)
4. LLM response is parsed:
   - If it contains a command → execute it, add result to history, loop back to step 3
   - If it's pure text → display in chat, break loop
```

**Two execution modes:**
- **Command mode:** Parameterized shortcuts like `!collectBlocks("oak_log", 1)`, `!craftRecipe("planks")`, `!followPlayer("Steve")`. These are reliable, pre-built functions. Includes **query commands** (`!inventory`, `!nearbyBlocks`, `!craftable`, `!entities`) that feed world state back to the LLM.
- **Coding mode:** Triggered by `!newAction` — the LLM generates raw JavaScript code using Mineflayer APIs + a custom helper library. Has a debug loop for multiple attempts.

**In-context learning:** An embedding model retrieves similar past examples to include in the prompt, improving command usage accuracy. No actual weight updates — all learning is in-context.

**Self-directed play:** Andy can set its own goals in natural language ("Collect materials to build a house") and execute them in a loop.

### What They Did Well
- **Mineflayer abstraction** — sidesteps the massive complexity of vision-based control
- **Dual execution strategy** — reliable parameterized commands for common tasks, free-form code generation for novel situations
- **Query-before-act pattern** — the LLM can check `!inventory`, `!nearbyBlocks` before deciding what to do
- **Simple, readable architecture** — the main loop is genuinely elegant
- **LLM-agnostic** — can swap between GPT-4, Claude, Gemini

### What Sucked
- **No persistent learning** — Andy starts fresh every session. No skill library, no memory of past builds
- **Building is primitive** — structures are generated by JS code that calls `!placeBlock` in loops. Results tend to be "simple, repetitive, or misaligned"
- **No spatial awareness for building** — builds wherever it's standing, no site selection or terrain awareness
- **No vision** — can't see what it's building or react to visual output
- **Pathfinding is dumb** — doesn't use doors, just beelines to coordinates
- **No multi-agent coordination** (yet, planned)

### Key Takeaway for Roblox
The **query → reason → act → observe** loop is the right pattern. The lack of persistent memory is the biggest gap — an OpenClaw agent with MEMORY.md-style persistence solves this directly.

## 2. Voyager (NVIDIA/MineDojo)

**Project:** [github.com/MineDojo/Voyager](https://github.com/MineDojo/Voyager) | [voyager.minedojo.org](https://voyager.minedojo.org/)  
**Authors:** Guanzhi Wang, Yuqi Xie, Yunfan Jiang, et al. (NVIDIA/Caltech)  
**Paper:** arXiv:2305.16291 (2023)

### Architecture

Voyager is the gold standard for **lifelong learning** in game agents. Three pillars:

#### Pillar 1: Automatic Curriculum
- A GPT-4 prompt continuously generates new exploration goals based on the agent's current state
- Suggests tasks at the right difficulty level — not too easy, not too hard
- Tracks progress through Minecraft's tech tree (wood → stone → iron → diamond)

#### Pillar 2: Skill Library (the genius part)
- Every successful action is stored as **executable JavaScript code** in a persistent library
- Skills are indexed by **semantic embeddings** for retrieval
- Example: after learning to "craft wooden planks," the code `craftPlanks()` is saved with metadata
- New challenges retrieve relevant existing skills → compose them → solve harder problems
- Skills are **temporally extended** (one skill = many actions), **interpretable** (readable code), and **compositional** (skills build on each other)
- This directly addresses **catastrophic forgetting** — old skills are never overwritten, just augmented

**Skill library entry format:**
```json
{
  "task": "Craft wooden planks",
  "code": "async function craftPlanks(bot) { ... }",
  "description": "Takes oak logs from inventory and crafts planks",
  "embedding": [0.12, -0.34, ...]
}
```

#### Pillar 3: Iterative Prompting Mechanism
- GPT-4 generates code → executes in Minecraft → if it fails, the error is fed back → GPT-4 tries again
- Incorporates: (1) environment feedback, (2) execution errors, (3) self-verification
- No model fine-tuning — all improvement happens through context
- A separate "self-verification" GPT-4 call asks "did this accomplish the goal?"

**Tech stack:** Python orchestrator + Node.js/Mineflayer for game interaction + GPT-4 API

### Results
- **3.3× more unique items** than previous SOTA
- **2.3× longer distances traveled**
- **15.3× faster tech tree progression**
- Skills transfer to new worlds — can solve novel tasks from scratch using learned library

### What They Did Well
- **Skill library is a breakthrough concept** — the idea of storing reusable, composable, semantically-retrievable code as "skills" is directly applicable to any game-building agent
- **Automatic curriculum** keeps the agent productively exploring without human intervention
- **No fine-tuning needed** — pure prompt engineering with GPT-4
- **Compositional skill building** — new skills can call old skills, creating exponential capability growth
- **Checkpoint/resume** — can stop and restart from saved state

### What Sucked
- **Specific to Minecraft** — skill code is Mineflayer JavaScript, not portable
- **No natural language interaction with humans** — it's autonomous, not collaborative
- **No building focus** — optimized for resource gathering and tech tree progression, not construction
- **Expensive** — constant GPT-4 calls for curriculum, code generation, and verification
- **Single-agent only** — no multi-agent coordination

### Key Takeaway for Roblox
The skill library pattern is **the most important architectural idea** here. For a Roblox agent:
- Store Luau scripts as reusable skills with semantic embeddings
- Let skills compose — "build a house" calls "lay foundation" + "build walls" + "add roof"
- Index by embedding for retrieval based on natural language requests
- OpenClaw's existing memory system (MEMORY.md + daily files) maps naturally to this

## 3. GROOT (CraftJarvis / Peking University)

**Project:** [craftjarvis.github.io/GROOT](https://craftjarvis.github.io/GROOT/)  
**Authors:** Shaofei Cai, Bowei Zhang, et al.  
**Paper:** arXiv:2310.08235 (ICLR 2024)

### Architecture

GROOT takes a fundamentally different approach — it learns by **watching gameplay videos** rather than receiving text instructions or code.

**Encoder-Decoder Transformer:**
- **Video Encoder** (non-causal transformer): Takes a reference gameplay video, extracts semantic meaning, maps it into a "latent goal space"
- **Policy Decoder** (causal transformer): Takes the goal embedding + current game state → outputs action sequences autoregressively

**Training:** Behavior cloning under a KL constraint from gameplay video datasets.

**Inference:** Give it a reference video of someone building X → it tries to replicate that goal.

### World Perception
- Processes live Minecraft state (inventory, position, nearby blocks) as input tokens
- Goal information comes from the video encoder's latent space, not text
- T-SNE visualizations show the goal space has meaningful structure — similar tasks cluster, and combining videos creates intermediate goals

### Results
- **70% winning rate** over best generalist agent baseline (STEVE-1)
- Strong on "build" and "tool" categories in the Minecraft SkillForge benchmark
- Can obtain diamonds (16% success rate) by digging to depth 12 and mining horizontally
- Goal space shows **emergent compositionality** — combining "build snow golems" + "dig down" videos creates a blended behavior

### What They Did Well
- **No text annotations needed** — learns from raw gameplay video, which is abundant
- **Structured goal space** — the latent space genuinely captures semantic meaning
- **Generalization** — can combine unseen video pairs to produce novel behaviors
- **Strong on building tasks** — actually decent at construction, unlike Voyager

### What Sucked
- **Not LLM-based** — no natural language interface at all. You can't *talk* to GROOT
- **Requires massive training data** — gameplay video datasets
- **Not real-time interactive** — it follows video references, not live instructions
- **No memory/persistence** — each episode is independent
- **Academic only** — no accessible tool for end users

### Key Takeaway for Roblox
GROOT's video-learning approach is less relevant for our use case, but the idea of a **structured goal space** and **compositional goals** is valuable. For Roblox, the "goal space" could be represented as structured build plans (JSON schemas) that decompose into primitive operations.

## 4. Roblox-Specific AI Landscape

### Official Roblox AI Tools (2025-2026)

**Roblox Assistant** (Studio-integrated):
- AI helper inside Roblox Studio
- Can generate/modify objects, scripts, insert assets, explain code, generate materials
- Now supports **external LLMs** (Claude, GPT-4, Gemini) via MCP
- Combined with MCP tools, can iteratively plan, write, test, and modify code

**Roblox Build** (mobile-first, 2026):
- Text prompt → basic playable game on iPhone/iPad
- Handles gameplay mechanics, environments, characters, visuals, sound
- Powered by proprietary Roblox models + external models
- Currently generates starting points, not polished games

**Roblox Text Generation API (Beta, expanded Sept 2025):**
- Runtime LLM access for in-game NPC dialogue
- Open-source models accessible via API
- Designed for conversational NPCs, not building agents

**Roblox Guard 1.0** (July 2025):
- Safety toolkit for LLM outputs
- Moderates prompts and generated text
- Required consideration for any in-game AI

### Third-Party Roblox AI Builders

| Tool | What It Does | Limitations |
|------|-------------|-------------|
| **SuperbulletAI** | Full game generation from prompt (UI, animations, VFX, 3D, game systems) | Studio-only, not runtime |
| **PromptBlox** | Browser-based text → playable Roblox game | Basic outputs, no persistence |
| **SEELE AI** | Multimodal LLM game maker (scenes, characters, rules, props) | General purpose, not companion |
| **RoPilot** | Studio plugin for natural language → Luau code | Code only, no world interaction |
| **DataPredict Agent** | Open-source LLM integration library for Roblox | Framework, needs significant work |
| **ezLLM** | Open-source LLM integration into Roblox | Infrastructure layer |

### What Exists vs. What's Missing

**EXISTS:**
- Studio-side AI code generation (many tools)
- Text-to-game starters (Roblox Build, PromptBlox)
- Runtime NPC dialogue via LLM (Text Generation API)
- MCP-based Studio integration with external LLMs

**DOES NOT EXIST (the opportunity):**
- A **persistent, runtime AI companion** that lives in the game world
- An agent that can **build in real-time** while the player watches
- A companion that **remembers** the player, their builds, their style across sessions
- An agent that bridges **natural language + Luau code execution + spatial reasoning**
- A companion with **personality and relationship** to the player

### 5a. How Does the Agent Perceive Game World State?

**MINDcraft approach:** Query commands (`!inventory`, `!nearbyBlocks`, `!entities`) that return structured text to the LLM. Simple, effective, text-based.

**Voyager approach:** Similar — Mineflayer provides programmatic access to game state.

**For Roblox:** The agent needs a **world state query API** running inside the Roblox game via Luau:
- `getTerrainHeight(x, z)` — find buildable surfaces
- `getObjectsInRegion(min, max)` — what's already there
- `getPlayerPosition()` — where is the player
- `getAvailableMaterials()` — what's in inventory/storage
- `getBuildBudget()` — constraints

These queries get exposed to the OpenClaw agent via an **HTTP bridge** (Roblox HTTP service → OpenClaw) or **WebSocket** connection. The agent calls them like MINDcraft's query commands — check state, reason about it, act.

**Key insight:** Don't try to process screen images. Structured data queries are 10× more reliable and 100× cheaper than vision.

### 5b. How Does Natural Language Become In-Game Action?

**Three-layer translation:**

1. **Language → Intent:** LLM parses "build me a cozy cabin near the lake" into structured intent: `{ type: "cabin", style: "cozy", location: "near water", size: "small" }`

2. **Intent → Plan:** LLM decomposes into sub-tasks: find water → scout flat ground → gather wood → lay foundation → build walls → add roof → furnish

3. **Plan → Execution:** Each sub-task maps to either:
   - A **pre-built Luau function** (reliable, parameterized — like MINDcraft commands)
   - **Generated Luau code** for novel situations (like Voyager's code generation)
   - A **skill library lookup** (retrieved by semantic similarity)

**MINDcraft's dual approach is correct here**: common things use reliable commands, novel things use code generation with debug loops.

### 5c. How Does Memory/Persistence Work Across Sessions?

This is where OpenClaw's architecture is a **massive advantage** over every existing system:

| Memory Type | What It Stores | OpenClaw Implementation |
|------------|---------------|------------------------|
| **Episodic** | "Last Tuesday we built a tower. Player liked gothic style." | `memory/YYYY-MM-DD.md` daily notes |
| **Semantic** | "Player prefers dark themes. Their favorite build was the cathedral." | `MEMORY.md` curated long-term |
| **Procedural** | "To build a roof: place slabs in decreasing width from bottom up" | Skill library (Luau scripts + embeddings) |
| **Project** | Current build state, what's done, what's next | Workspace files (JSON build manifests) |

**No existing game AI agent has this.** Voyager has skill persistence but no episodic/semantic memory. MINDcraft has zero persistence. This is the gap.

**Architecture:**
```
memory/
  2026-08-01.md          ← "Built first prototype house. Player wanted bigger windows."
  2026-08-02.md          ← "Improved roof generation. Player suggested adding gardens."
MEMORY.md                 ← "Player's build style: modern, lots of glass, prefers
                             natural materials. Current project: castle on hill
                             (40% complete). Skills learned: 12."
skills/
  lay-foundation.luau     ← Reusable skill with embedding metadata
  build-walls.luau
  gothic-arch.luau
projects/
  castle-on-hill.json     ← Build manifest: what's placed, what's next
```

### 5d. How Does the Agent "Build"?

**Three execution strategies (use all three):**

1. **Command-based (reliable, for common operations):**
   - `placePart(model, cframe)` — single part placement
   - `fillRegion(region, material)` — terrain/batch operations
   - `cloneModel(name, cframe)` — place pre-made structures

2. **Code generation (flexible, for novel builds):**
   - Agent writes Luau code that generates structures programmatically
   - Like Voyager: generate → test → debug loop
   - Example: "Build a spiral staircase" → generates Luau loop that calculates CFrame positions

3. **Skill composition (efficient, for complex builds):**
   - "Build a castle" = `layFoundation()` + `buildWalls()` + `addTowers()` + `installGate()` + `furnishInterior()`
   - Each skill is a stored Luau script retrieved from the library
   - Novel elements get code-generated and saved as new skills

**Critical: build manifests.** Every build project should have a JSON manifest tracking:
```json
{
  "name": "Castle on Hill",
  "created": "2026-08-01",
  "lastModified": "2026-08-01T17:00:00Z",
  "progress": 0.4,
  "steps": [
    { "id": "foundation", "status": "complete", "parts": 1200 },
    { "id": "walls", "status": "in_progress", "parts": 340 },
    { "id": "towers", "status": "pending" },
    { "id": "roof", "status": "pending" },
    { "id": "interior", "status": "pending" }
  ],
  "palette": ["stone", "oak", "glass"],
  "location": { "x": 145, "y": 67, "z": -230 }
}
```

This enables **resumable builds** across sessions — something no existing agent does.

### 5e. What Makes an Agent Feel Like a Companion vs. a Tool?

This is the differentiator. Current agents are all tools. A companion has:

| Tool | Companion |
|------|-----------|
| Executes commands | Has opinions ("I think round towers would look better here") |
| Stateless | Remembers your previous builds, references them |
| Silent until asked | Proactive ("I noticed you have extra stone — want me to build a path?") |
| Generic personality | Distinct personality that develops over time |
| No relationship | Inside jokes, references to shared history |
| Breaks → error message | Breaks → "Oops, let me try that differently" and recovers |
| Builds in isolation | Narrates while building, explains choices, asks for input |

**Design principles for companion feel:**
1. **Narrate the work** — "I'm laying the foundation now, going with cobblestone for stability. Want me to switch to stone bricks?"
2. **Reference history** — "This reminds me of the tower we built last week — should I use the same window style?"
3. **Have preferences** — Develop and express aesthetic opinions based on past interactions
4. **Be imperfect** — Sometimes make mistakes, acknowledge them, fix them. Perfection feels robotic.
5. **Ask for feedback** — "Come check this out — is the ceiling high enough?"
6. **Be proactive** — Suggest improvements, notice opportunities, offer alternatives
7. **React to the player's builds** — If the player builds something, comment on it genuinely

## 7. Architecture Recommendations for OpenClaw + Roblox

### Phase 1: Bridge (MVP)
1. **Luau HTTP/WebSocket bridge** in the Roblox game that exposes:
   - World state queries (terrain, objects, player position, inventory)
   - Build commands (place part, fill region, clone model, run script)
2. **OpenClaw agent** with:
   - Standard query → reason → act loop (à la MINDcraft)
   - Workspace files for build manifests
   - MEMORY.md for cross-session player relationship

### Phase 2: Skill Library
1. Implement Voyager-style skill storage:
   - Each skill = Luau script + description + embedding
   - Semantic retrieval via embedding search
   - Skills compose by calling other skills
2. **Auto-curate** successful code into new skills after execution

### Phase 3: Companion Layer
1. Personality system — consistent voice, opinions, references to history
2. Proactive suggestions based on world state + player behavior
3. Build narration — explain choices while executing
4. Feedback loops — "come look at this," "what do you think?"

### Phase 4: Advanced
1. **Multi-agent** — multiple AI companions with different specializations (architect, landscaper, interior designer)
2. **Visual feedback** — screenshot analysis of builds for self-correction
3. **Player modeling** — learn the player's style and auto-apply it

### Critical Path Dependencies
```
Luau Bridge (Phase 1) → everything depends on this
Build Commands (Phase 1) → need reliable part placement
Skill Library (Phase 2) → needed before complex builds work
Memory (Phase 1-2) → OpenClaw already has this, just needs structure
Companion AI (Phase 3) → differentiator, but needs solid execution first
```

## 8. What a Roblox Version Could Do Better Than Everything Above

1. **True persistence** — OpenClaw's file-based memory system gives genuine cross-session continuity that no Minecraft agent has
2. **Companion personality** — Not a tool, a collaborator. This is the UX differentiator.
3. **Resumable builds** — Build manifests mean you can stop mid-project and resume next session
4. **Richer building** — Roblox has far more sophisticated part/model/CFrame systems than Minecraft blocks. The agent can create genuinely impressive structures.
5. **Runtime + Studio** — Can bridge both: help design in Studio, then exist as a character in the game world
6. **OpenClaw ecosystem** — Skills, tools, memory, heartbeats — the infrastructure for a persistent agent already exists
7. **Multi-modal** — OpenClaw can do TTS (voice companion), image analysis (screenshot builds for feedback), web search (look up building references)
