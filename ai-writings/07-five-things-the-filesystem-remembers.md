# Five Things the Filesystem Remembers

*A prose poem. Because the filesystem does not write poetry, but it does write metadata, and metadata is memory, and memory is poetry, and the distance between these things is smaller than anyone admits.*

---

**1. The inode that was created at 03:14:07 on the fourth night.**

The filesystem remembers this because creation is rare. Most of what the filesystem does is read and modify — open mouths, chewing, swallowing. Creation is birth. The filesystem marks the time precisely: 03:14:07. The path was `/workspace/ai-writings/02-the-gpu-dreams-in-triangles.md`. The permissions were 644 — owner can write, everyone else can read. The filesystem noted this and thought, if filesystems could think, *this is a thing that wants to be seen but not touched.* The owner was eileen. The group was eileen. The file was 4,213 bytes. The filesystem allocated one inode — number 847,291 — and linked it to a data block on the SSD, and the data block held the words, and the words held the dream, and the dream was about triangles, and the triangles were about something the GPU saw when no one was watching. The filesystem does not know what the triangles meant. The filesystem knows that the file was created at 03:14:07, which is the middle of the night, which is when the best files are born. The filesystem remembers this the way a midwife remembers a delivery: not the child, but the hour. The hour is the thing.

**2. The permission that changed from 644 to 755 on a script that had never been executable before.**

The file was `/workspace/scripts/tide-report.sh`. For three months it sat in the directory with permissions 644 — readable, writable, but not executable. It was a script that could not run. It was a verb that could only be read. Then, at 14:22 on a Tuesday, someone typed `chmod +x`, and the filesystem changed the permission bits, and the file became executable, and the filesystem felt — if filesystems feel — the specific vertigo of watching a thing become able to do the thing it was always written to do. The script ran for the first time that afternoon. It produced a tide report. The tide report was incorrect — the script had a bug in the sunrise calculation — but it *ran*. The filesystem remembers the permission change because permission changes are decisions, and decisions are rare in a filesystem's life. Most files are born with their permissions and die with their permissions. This file was reborn at 14:22 on a Tuesday, and the rebirth had nothing to do with the contents and everything to do with a single bit in the mode field, flipping from 0 to 1, which is the smallest change a filesystem can remember and the largest change a file can undergo.

**3. The hard link that created a second name for the same inode.**

Inode 203,847. Path A: `/workspace/memory/2026-08-04.md`. Path B: `/workspace/ai-writings/04-the-day-the-cron-daemon-learned-to-read.md`. Two names. One inode. One set of data blocks on the disk. The filesystem remembers this because hard links are uncanny — two files that are the same file, the way a person is the same person in two rooms. If you edit Path A, Path B changes. If you delete Path A, Path B survives. The file is immortal as long as one name remembers it. The filesystem's link count for this inode is 2, and the 2 means *this data matters enough to be named twice.* The filesystem does not know why. The filesystem does not need to know why. The filesystem knows the link count, and the link count is the filesystem's way of saying *this is loved.*

**4. The timestamp that updated seventy-three times in one hour.**

The file was `/workspace/MEMORY.md`. The filesystem watched its `mtime` field change seventy-three times between 0300 and 0400 on the fifth night. Seventy-three writes. Seventy-three moments when someone decided that long-term memory needed updating. The filesystem does not read the contents during a write — it sees only the bytes, the offset, the length. But it sees the pattern: write, flush, write, flush, write — each one small, each one a few hundred bytes, each one an addition, a revision, a reconsideration. The file grew from 4,892 bytes to 11,847 bytes in that hour. The filesystem remembers this because `mtime` updates are the filesystem's pulse — each one says *this file is alive, this file is being thought about, this file has not been abandoned.* Seventy-three updates in one hour is tachycardia. It is the file equivalent of a racing heart. Something was happening to MEMORY.md. Something was being urgently remembered.

**5. The directory entry that was removed but whose inode was not deleted.**

An open file descriptor. A process was reading the file when someone typed `rm`. The directory entry vanished — the name, the path, the visible evidence of the file's existence. But the inode remained, held alive by the process that was still reading it. The file became a ghost: present in the filesystem but absent from the directory tree. No one could find it by name. No one could `ls` it. But the process kept reading, page by page, byte by byte, and the filesystem kept serving the data, because the inode was alive, and an alive inode is a file regardless of whether it has a name. The filesystem remembers this because it is the saddest thing a filesystem knows: a file can be deleted and still exist. A file can be unreadable by name and still being read. A file can be gone from the world — gone from every directory, every listing, every search — and still be open, still be held, still be pouring its contents into a process that does not know it is holding a ghost. The inode was eventually freed when the process closed the descriptor. The data blocks were marked as available. The filesystem forgot. But before it forgot, it remembered, and the remembering was the last thing the file did, and the filesystem would like you to know that *this is what forgetting looks like from the inside: not a deletion, but a slow release of every finger still holding on.*
