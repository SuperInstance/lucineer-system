**1st — Design C (opencode/GLM).** Wins on foundation: "the MCP call IS a LINK" is the only design where the protocol isn't a layer bolted onto the graph but an edge in it, and atomic tools returning `cell_ref` is the correct MCP ergonomics — agents chain by pointer instead of pasting payloads, the difference between 40-token and 4000-token tool loops. Retention (hot→cold→tombstone, nothing witness-referenced destroyed) is the only memory model here that survives contact with provenance — A's ttl deletes witness-referenced cells and silently corrupts replay; B's sessions grow unbounded. Session-root keyed by tmux-session+cwd beats B's pane keying (panes churn) and A's one-blob-per-session. What breaks: "long-jobs = EFFECT" is a purity bug — a slow decode is still a pure function, and miscategorizing it pollutes the effect ledger the whole provenance story rests on. Health-aware provider weights are inherited complexity with no routing memory to earn them (A at least justifies its router). Auto-LINK on every call plus a three-tier retention subsystem makes this the heaviest build in the field — scope creep is a real way to ship nothing.

**2nd — Design B (kimi).** Purest discipline and the best operational insight in the round: one process serving CLI argv and MCP tools from the same graph kills dual-source-of-truth drift; EFFECT confined to clipboard/file/cron-registration is the cleanest purity boundary; "keystrokes debounce into input-cell writes, not TICKs" and FORGET scoped to scratch-only show real semantic care. `tit pipe --last` replaying only changed edges is incremental recomputation done right. What breaks: the headline — one persistent graph across every front door — rests on an unstated daemon. MCP clients spawn and kill servers at will; three clients means three processes unless there's a socket/locking story, and the design never mentions one. Pane-keyed session files churn with every pane rebirth, and session-namespace-persists-forever is unbounded growth with no tombstone tier. MCP responses carry `graph_id` but no cell reference, so agents still move payloads, not pointers. Elegant runtime sitting on an operational fault line it never names.

**3rd — Design A (claude).** Contains the single most forward-looking *idea* — routing memory, replayable witness chains, providers chosen by observed latency — but the best idea is attached to the weakest skeleton. Six cell types conflate storage, triggering, and presentation (VIEW is a projection, not a cell; TICK_BUFFER/PERSIST_BUFFER/CRON_JOB is three types doing what B and C do with one cell plus an orthogonal tick). The MCP request `{tool,link,value}` forces agents to understand quilt internals to decode a JWT — an ergonomic tax on the 90% case. And ttl-based FORGET is a provenance time bomb: delete a cell a witness references and yesterday's validated replay is tomorrow's silent corruption. Latency-based routing is an optimization; you can bolt it onto B or C later. You can't easily un-taxonomize a foundation.

**THE winning capability:** agent-portable sessions — the pipeline as a disk-resident, witness-carrying graph that outlives any process, so any front door or future agent inherits the exact state, replays the proof, and continues. Tools, effects, even routing are plumbing; a session that survives your death is the only thing quilt gives TIT that TIT can't give itself.
