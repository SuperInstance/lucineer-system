# KIMI MOLT ANALYSIS — Training Slackwater's Build Agents with Reinforcement Learning

*Spatial architect / build-intelligence assessment for the Slackwater project.*

---

## 1. EXECUTIVE SUMMARY

NVIDIA's **MOLT** ([labs-molt](https://github.com/NVIDIA-NeMo/labs-molt), [arXiv:2607.21653](https://arxiv.org/abs/2607.21653)) is a PyTorch-native, agentic-first reinforcement-learning framework. Its core contract is simple: **the agent is an ordinary program; reward is any Python you write inside an `Env` or `ChatAgent`; one async loop trains the policy on tokens the policy itself generated**. For Slackwater, this is the missing bridge between "generate a build from scratch with a 5-model pipeline" and "agents that learn from every structure players keep, fix, delete, or share."

This document proposes a **build-quality reward system** that turns live player behavior into a training signal for Lucineer and the builder agents. Instead of treating each `build me a waterwheel` request as an isolated inference, we treat it as one episode. The rollout is the JSON command sequence that materializes parts in Roblox. The reward is computed days later from telemetry. MOLT's single-actor, vLLM-backed trainer turns those (prompt, command-trace, reward) tuples into a policy update.

The result: a **data flywheel** where every build makes the next build better, and where the agents develop region-specific, era-specific, player-specific tacit knowledge about what "good" means in Slackwater.

## 2. WHAT MOLT IS — AND WHY IT MAPS TO SLACKWATER

### 2.1 MOLT's design surface (what matters for us)

| MOLT feature | Why it fits Slackwater |
|--------------|------------------------|
| **Agent = ordinary Python program** | We can write a Slackwater `Env` whose `step()` dispatches against the existing `CommandExecutor` schema (`createPart`, `addLight`, `markUnfinished`, etc.). |
| **Reward = any Python** | Perfect for our mixed signal landscape: kept-time, adjacency, screenshots, visits, storm survival, deletion. No rigid reward model required. |
| **Token-first contract** | A Roblox build is already a token-like sequence of commands. MOLT can train directly on command-token trajectories produced by Qwen3-Coder / Qwen3.6. |
| **Single actor + optional critic** | We do not need a separate reward-model team. The same Qwen3.6-35B (or a smaller fine-tuned policy) becomes the build actor. |
| **VLM + multi-turn tool support** | The perception path (Qwen3-VL screenshots) can be folded into observations; agents can call world-query tools (`getTerrainHeight`, `raycastStability`). |
| **RLOO / GRPO / PPO estimators** | Ideal for sparse, high-variance build rewards. Group baselines compare multiple candidate layouts for the same prompt. |

### 2.2 The paradigm shift: from inference-only to learn-from-every-build

Current Slackwater pipeline (UNIFIED_INTEGRATION_PLAN §1):

```
Player request → Seed-mini (intent) → Qwen3.6 (spatial plan) → Qwen3-Coder (commands)
                → Hermes (voice) → Nemotron-Safety → CommandExecutor → parts appear
```

This is **stateless**. Model weights are frozen. A bad waterwheel today is generated by the same policy that made a bad waterwheel yesterday.

MOLT-enabled pipeline:

```
Player request → Seed-mini (intent) → RL policy (spatial plan + commands)
                → Qwen3-Coder (JSON harden) → Hermes (voice) → Safety → parts appear
                ↓ (hours to days)
                Telemetry → Reward computer → MOLT trainer → updated policy weights
```

The RL policy can start from Qwen3.6-35B-A3B or from a smaller distilled model (Qwen3-4B, Nemotron-Nano-Omni) and is fine-tuned specifically on build trajectories. Qwen3-Coder and Hermes remain in the loop as refiner and voice layer, but the *spatial intelligence* — what goes where, what to leave unfinished, how to brace for storms — becomes trainable.

## 3. BUILD-QUALITY REWARD SYSTEM

### 3.1 Reward philosophy

A "good build" in Slackwater is not an aesthetic score. It is a **behavioral score**: the build caused players to act in ways that indicate value. We deliberately avoid hand-crafted rubrics ("symmetry = +0.1") and instead derive the reward from observed player behavior, with a small set of physical-safety shaping terms.

### 3.2 Signal taxonomy and weights

All signals are normalized to a per-build reward in the range roughly `[-2.0, +8.0]`. Weights below are starting hypotheses and should be tuned with a small held-out player panel.

#### Positive signals

| Signal | Definition | Reward | Rationale |
|--------|------------|--------|-----------|
| **Keep > 24h** | Build still exists and is un-deleted one full real-world day after creation. | `+1.0` | The lowest bar for "not garbage." Players delete junk quickly. |
| **Keep > 7d** | Build survives a week. | `+1.5` (cumulative with 24h) | Long-term retention is strong evidence of value. |
| **Player builds adjacent** | Player places a new part within `r = 20 studs` of the agent build in a later session. | `+0.4` per adjacent part, cap `+2.0` | The build became infrastructure — a seed for further creation. |
| **Player modifies it** | Player edits, re-colors, re-sizes, or re-orients an agent-placed part. | `+0.6` | Modification is deeper engagement than passive keeping. |
| **Completes a hook** | Player fills in a `markUnfinished` gap. | `+3.0` | The central bond-system moment; highest positive signal. |
| **Screenshots it / Build Card created** | Client captures a screenshot or generates a Build Card. | `+2.0` | Strong indicator of pride / shareability. |
| **Other players visit** | Unique players spend > 60 seconds within `r = 50 studs`. | `+0.3` per unique visitor, cap `+3.0` | Social proof; the build became a destination. |
| **Copied or blueprinted** | Player duplicates the build or requests "build another like this." | `+1.5` | Players want to reproduce the design. |
| **Survives a storm** | Build takes < 10% damage during a storm tide. | `+1.5` | Engineering validation; the structure is structurally sound. |
| **Used in a recipe** | Build becomes input to a crafting recipe (e.g., waterwheel → mill). | `+1.0` | Functional integration into the tech tree. |

#### Negative signals

| Signal | Definition | Reward | Rationale |
|--------|------------|--------|-----------|
| **Deleted within 1h** | Player deletes the entire build or all agent-placed parts within an hour. | `-1.0` | Strong rejection. |
| **Deleted within 24h** | Deleted within a day but not within an hour. | `-0.5` | Mild rejection. |
| **Abandonment decay** | Build untouched by owner for N days after initial interaction. | `-0.05 × N`, floor `-1.0` | Passive decay prevents reward hacking by inert leftovers. |
| **Storm destroyed** | Build takes > 50% damage in a storm. | `-0.8` | Structural failure signal. |
| **Safety / policy violation** | Nemotron-Safety flags output, or build contains prohibited shapes. | `-2.0` (hard clip) | Non-negotiable guardrail. |
| **Player undoes / Ctrl-Z** | Build is immediately undone. | `-0.7` | Instant regret. |

### 3.3 Composite reward formula

```python
R_build = (
    R_retention
  + R_engagement
  + R_social
  + R_structural
  + R_safety
)

# Per-signal sub-components
R_retention   = 1.0 * I(keep_24h) + 1.5 * I(keep_7d) - 0.05 * clamp(days_abandoned, 0, 20)
R_engagement  = 0.4 * clamp(adjacent_parts, 0, 5) + 0.6 * I(modified) + 3.0 * I(hook_completed)
                + 2.0 * I(screenshot) - 0.7 * I(undone)
R_social      = 0.3 * clamp(unique_visitors, 0, 10) + 1.5 * I(copied_or_repeated)
R_structural  = 1.5 * I(storm_survived) - 0.8 * I(storm_destroyed)
R_safety      = -2.0 * I(policy_violation)

# Optional: normalize by player engagement baseline so high-activity players don't dominate
R_build_norm = R_build / (1.0 + 0.1 * weekly_player_sessions)
```

**Why normalize by engagement?** A hyper-active player who screenshots everything would otherwise drown out a quiet player who only screenshots one perfect bridge. Per-player baseline division keeps the reward about *relative* quality, not *absolute* activity.

### 3.4 Reward timing and episode terminality

A build episode is **terminal** when one of the following occurs:

1. Build is deleted (reward locked in, negative).
2. Build survives 7 days (reward capped and finalized).
3. Player explicitly archives / blueprint / publishes it (reward finalized).
4. Build is destroyed by storm (reward finalized).

Until terminality, the reward is a **running estimate**. MOLT supports multi-turn episodes, but for build quality we can also train on *finalized* episodes in an offline RL mode first, then move to online RL with delayed rewards.

## 4. CREDIT ASSIGNMENT — WHO GETS THE REWARD?

This is the hard problem. A bridge that players love is made of 200 `createPart` commands. Which commands caused the success?

### 4.1 Granularity levels

| Level | What we track | Use case |
|-------|---------------|----------|
| **Episode-level** | Entire command sequence gets the final reward. | Initial MOLT training; simple; high variance. |
| **Command-level** | Each `createPart` / `addLight` / `markUnfinished` gets a reward based on what happened to that part. | Better credit; requires deletion-part attribution. |
| **Part-level** | Each physical part in Roblox is tracked with a persistent ID and a survival/engagement score. | Best spatial credit; allows fine-grained learning. |

### 4.2 Part-level attribution algorithm

Every part created by an agent gets a `part_id` stored in the Roblox `Attributes` or a lookup table in D1. We then compute per-part outcomes:

```python
# For each part i in build B
part_quality[i] = (
    +0.5 * I(part_exists_at_24h)
  + 0.3 * I(part_modified_by_player)        # player cared enough to edit it
  + 0.4 * I(nearby_part_placed_by_player)   # it became anchor for player work
  - 0.5 * I(part_deleted_first)             # early deletion signals bad placement
  + 0.2 * I(part_survived_storm)
)
```

The episode reward is then decomposed as:

```python
R_build_decomposed = Σ_i part_quality[i] / max(N_parts, 20) + R_bonus_signals
```

where `R_bonus_signals` captures whole-build events (screenshot, visit, hook completion) that cannot be attributed to a single part.

This decomposition lets MOLT's policy gradient assign higher credit to command tokens that produced high-quality parts.

### 4.3 The "markUnfinished" special case

A `markUnfinished` command is a **deliberate gap**. If the player later fills it, the gap command and the surrounding parts should receive a large positive bonus. If the player deletes the build because the gap was confusing, the gap command should receive negative credit. This is critical because the Unfinished Rule is the keystone of Slackwater's character loop (UNIFIED_INTEGRATION_PLAN §2, Insight 1).

```python
if hook_completed:
    bonus_gap = +3.0  # distributed to markUnfinished command and adjacent parts
elif hook_deleted:
    bonus_gap = -1.0  # the gap was poorly placed or poorly communicated
```

## 5. MOLT AGENT CONTRACT FOR SLACKWATER

We implement a MOLT `Env` subclass, not a `ChatAgent`, because we want the framework to own token generation while we own the world-evaluation logic.

### 5.1 Observation space

```python
observation = {
    "intent_text": "build me a waterwheel for the stream",
    "era": 2,
    "available_recipes": ["waterwheel", "gear", "drive_shaft", ...],
    "player_bond_stage": 3,
    "player_preferences": "likes timber frames, leaves gaps",
    "world_state_vector": {
        "terrain_height": [...],
        "water_flow_dir": (x, y, z),
        "nearby_player_builds": [...],
        "biome": "coastline",
        "tide_phase": "falling",
        "salvage_inventory": {"wood": 12, "iron": 3}
    },
    "top_k_skills_from_vectorize": [...],  # recalled from Vectorize
    "previous_build_summary": "last build: windmill, kept 5d, screenshot"
}
```

The observation is serialized to text for the LLM actor (Qwen3.6 or policy model). Vision observations can be added later by feeding Qwen3-VL screenshots into a multimodal policy.

### 5.2 Action space

Action is a JSON array of commands in the existing `CommandExecutor` schema:

```json
[
  {"command": "createPart", "params": {"name": "wheel_rim_1", "shape": "Cylinder", "position": [12, 3, 8], "size": [4, 0.5, 4], "material": "Wood", "rotation": [0, 15, 0]}},
  {"command": "createPart", "params": {"name": "wheel_spoke_1", "shape": "Block", "position": [12, 3, 8], "size": [0.3, 3.5, 0.3], "rotation": [0, 15, 0]}},
  {"command": "markUnfinished", "params": {"name": "axle_hook", "position": [12, 3, 10.5], "hint": "the axle needs a bearing"}}
]
```

MOLT will train the policy's token probabilities over this JSON. To reduce action-space size, we can first train a **command-type policy** (predict next command type given state), then a **parameter policy** (fill in values), mirroring the existing two-stage pipeline.

### 5.3 Reward function inside the Env

```python
from molt.agents import Env, Result

class SlackwaterBuildEnv(Env):
    async def step(self, state) -> Result:
        action_json = state["action_text"]
        build_id = await self.deploy_to_roblox(action_json)
        reward = await self.await_player_judgment(build_id, timeout_days=7)
        return Result(
            reward=reward,
            terminated=True,  # build episode ends when judged
            info={"build_id": build_id, "n_parts": len(action_json)}
        )
```

In practice, the `await_player_judgment` is not synchronous. We run MOLT in **offline mode**: collect finalized build episodes, then launch a training job on the batch.

## 6. DATA FLYWHEEL ARCHITECTURE

### 6.1 System diagram

```
┌─────────────────────────────────────────────────────────────────────────┐
│                           ROBLOX CLIENT                                  │
│  CommandExecutor materializes parts  →  TelemetryEmitter logs events     │
│  (part created, modified, deleted, screenshot, visitor, storm damage)   │
└───────────────────────────────┬─────────────────────────────────────────┘
                                │ HTTP
┌───────────────────────────────▼─────────────────────────────────────────┐
│                     CLOUDFLARE WORKER / DURABLE OBJECT                   │
│  • Build metadata → D1                                                   │
│  • Telemetry events → Analytics queue → D1 time-series                   │
│  • Build command traces → R2 (prompt + command JSON)                     │
└───────────────────────────────┬─────────────────────────────────────────┘
                                │ nightly
┌───────────────────────────────▼─────────────────────────────────────────┐
│                    REWARD COMPUTER (Cloudflare Worker or GPU pod)        │
│  • Read finalized build episodes from D1/R2                              │
│  • Compute R_build per episode                                           │
│  • Decompose to part-level credit                                        │
│  • Emit training examples: (prompt, command_trace, reward, info)         │
└───────────────────────────────┬─────────────────────────────────────────┘
                                │
┌───────────────────────────────▼─────────────────────────────────────────┐
│                    MOLT TRAINER (GPU cluster / DeepInfra)                │
│  • Load policy: Qwen3.6-35B-A3B or distilled Qwen3-4B                    │
│  • Estimator: GRPO or RLOO (variance reduction for sparse rewards)       │
│  • Train on batch; export LoRA / full weights                            │
└───────────────────────────────┬─────────────────────────────────────────┘
                                │
┌───────────────────────────────▼─────────────────────────────────────────┐
│                    DEPLOYMENT                                            │
│  • Updated weights → vLLM inference pod                                  │
│  • New builds generated by improved policy                               │
└─────────────────────────────────────────────────────────────────────────┘
```

### 6.2 Vectorize integration

The existing Vectorize index stores 55+ skill embeddings. MOLT training should **augment**, not replace, this:

- High-reward build trajectories are embedded with BAAI/bge-m3 and written to Vectorize as new "skills."
- At inference time, the processor recalls top-3 similar skills and includes them as few-shot examples in the prompt.
- This gives us a **dual memory**: Vectorize for fast episodic recall, MOLT weights for implicit policy improvement.

### 6.3 Cold-start strategy

At launch, no player-telemetry exists. We bootstrap with:

1. **Synthetic reward model**: Use Nemotron-Ultra-550B as an LLM-as-judge. Feed it the prompt and command JSON; ask it to score structural soundness, era appropriateness, and likely player retention. This generates synthetic `R_build` for existing template builds.
2. **Human curator set**: 200 hand-labeled good/bad builds from the team.
3. **Storm simulator**: Run physics checks on generated structures before deployment to assign a prior structural reward.

Once 1,000 real finalized episodes exist, synthetic rewards are down-weighted to 20% and then 0%.

## 7. ERA-SPECIFIC REWARD CURRICULA

Slackwater's seven eras are not just content gates; they are **learning curricula**. The reward function should change emphasis per era.

| Era | Build focus | Reward emphasis |
|-----|-------------|-----------------|
| **1 — Simple Machines** | Levers, pulleys, waterwheels | Structural stability (+), clarity of mechanical function (+), over-building (-). |
| **2 — Power Transmission** | Shafts, belts, gear trains | Power-flow connectivity (+), correct RPM ratios (+), friction losses (-). |
| **3 — Electricity** | Dynamos, wiring, lamps | Circuit completeness (+), wire routing elegance (+), short-circuit hazards (-). |
| **4 — Control Systems** | Sensors, relays, logic | Correct trigger behavior (+), feedback-loop stability (+), false positives (-). |
| **5 — Programmable Logic** | Arduino-style devices | Code-function match (+), player-modifiable code (+), opaque black-box (-). |
| **6 — Networked Systems** | Wireless, mesh, protocols | Topology robustness (+), packet-flow clarity (+), single-point-of-failure (-). |
| **7 — Autonomous Agents** | Agent factories, swarms | Fleet coordination (+), self-repair (+), resource starvation (-). |

Each era adds new command types and new failure modes. We should not train one policy across all eras from day one. Instead:

- Train separate LoRA adapters per era, or
- Prefix the prompt with an era token and train a single policy with era-conditioned prompts.

The second approach is simpler and lets MOLT's group baselines compare candidate builds within the same era.

## 8. TRAINING ALGORITHM CHOICE

MOLT supports several estimators. For Slackwater builds, we recommend:

### 8.1 Stage 1 — Offline RL with `reinforce_baseline` or `rloo`

- **Why**: We have a fixed batch of finalized episodes. We want to update the policy once per night.
- **RLOO** (Reinforce Leave-One-Out) removes the need for a learned value function and handles sparse rewards well when we have multiple samples per prompt.
- For each build prompt, generate `N=4` candidate command traces; the reward of each trace is compared against the average of the group.

### 8.2 Stage 2 — Online RL with `grpo` or `dr_grpo`

- **Why**: As the game runs, we want the policy to improve continuously.
- **GRPO** (Group Relative Policy Optimization) is MOLT's recommended group-baseline estimator and is designed for exactly this: high-variance, verifiable-reward tasks.
- **DR-GRPO** adds variance reduction; useful once we have thousands of episodes per day.

### 8.3 KL regularization

Use `--algo.kl.init_coef 0.01` to prevent the policy from drifting too far from the base Qwen3.6 model. We want Lucineer to keep his voice and safety characteristics; we only want his spatial reasoning to improve.

## 9. RISKS AND MITIGATIONS

| Risk | Severity | Mitigation |
|------|----------|------------|
| **Reward hacking** — agent builds indestructible cubes that survive storms but are useless. | High | Reward is dominated by engagement/social signals, not just survival. Require positive engagement signal to get high reward. |
| **Exploitation of screenshot signal** — players screenshot ugly failures. | Medium | Use Build Card creation (intentional share) rather than raw screenshot; normalize by player's screenshot rate. |
| **Sparse reward / long delay** — build judgment can take days. | High | Start with offline RL on finalized batches; use synthetic reward model for fresh prompts; accept delayed updates. |
| **Credit assignment noise** — players delete for reasons unrelated to quality (needed space, changed plan). | Medium | Normalize by player deletion baseline; use part-level attribution; require multiple negative signals before strong penalty. |
| **Policy collapse to one template** | High | Group baselines + KL penalty + era conditioning; maintain a diversity bonus (`-entropy` regularization). |
| **Safety drift** | Critical | Keep Nemotron-Safety as a hard filter; clip reward at `-2.0` for any flagged output; include safety examples in every batch. |
| **Compute cost** | Medium | Fine-tune a 4B–8B policy with LoRA instead of full 35B updates; train weekly, not nightly, until scale justifies it. |
| **Multiplayer fairness** — player A's world should not become a training ground that hurts player B. | Medium | Per-world policy versions; A/B test new weights on a fraction of sessions; rollback on engagement drop. |

## 10. 30 / 60 / 90-DAY ROADMAP

### 30 days — Telemetry and synthetic reward

- Instrument every `createPart`, `markUnfinished`, delete, modify, screenshot, visit, and storm-damage event.
- Store (prompt, command trace) pairs in R2 with build IDs.
- Build the Reward Computer as a Cloudflare Worker that can score historical builds using the synthetic Nemotron judge.
- Generate 1,000 synthetic training examples and run one MOLT `reinforce_baseline` job on Qwen3-4B to prove the loop.

### 60 days — Closed-loop learning

- Real telemetry is flowing; compute `R_build` for finalized episodes.
- Train a LoRA on Qwen3.6-35B-A3B using MOLT + RLOO.
- A/B test: 50% of players get the RL policy, 50% get the baseline 5-model pipeline.
- Measure: retention of builds at 24h, screenshot rate, hook completion rate.

### 90 days — Continuous improvement

- Move to online GRPO with daily or weekly weight updates.
- Integrate Qwen3-VL perception observations (screenshots as state).
- Roll out era-specific reward curricula and per-era LoRA adapters.
- Publish a "Hall of Evolved Builds" where the highest-reward designs become templates for new players.

## 11. KEY QUESTIONS TO ANSWER BEFORE BUILDING

1. **Do we have enough telemetry storage?** Each build command trace is ~5–20 KB of JSON. At 10,000 builds/day, that is 50–200 MB/day. R2 is fine; D1 may need partitioning.
2. **Which model becomes the RL actor?** Qwen3.6-35B is our spatial planner today but is expensive to train. A fine-tuned Qwen3-4B or Nemotron-Nano-Omni may be sufficient for command generation if Qwen3-Coder remains as refiner.
3. **How do we handle the `markUnfinished` ambiguity?** Lucineer sometimes leaves a gap *because* it should be completed; sometimes because it should not. We need to label gap intent.
4. **What is the rollout termination condition for un-deleted builds?** We propose 7-day cap, but this should be validated against player session patterns.
5. **Can we run MOLT on DeepInfra or do we need our own GPU cluster?** MOLT is infrastructure, not just an API. DeepInfra gives us inference; training likely requires dedicated A100/H100 nodes or a managed RL service.

---

## 12. CONCLUSION

MOLT turns Slackwater's builder agents from prompt-response engines into **learning systems**. The critical insight is that every build is a rollout and every player action is a reward signal. By constructing a reward function around retention, adjacency, modification, social sharing, and storm survival — and by using MOLT's `Env` contract to train on those signals — we can make Lucineer genuinely better at building the longer the game runs.

The 5-model pipeline does not go away. It becomes the **generator of candidates**, while MOLT becomes the **selector and improver** of candidates based on what players actually value. That is the difference between a game that ships with good AI and a game whose AI becomes better than anything we could have designed.
